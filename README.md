# B2C Ourbox Sales Dashboard

아워박스 B2C 매출 진척도 대시보드와 Google Sheets 기반 데이터 파이프라인 작업 기록입니다.

## 현재 운영 구조

- 대시보드 원본(사람이 고치는 파일): `dashboard.src.html`
- 운영 배포 파일(자동 생성): `index.html`
- 빌드 스크립트: `build_index.py`
- 캐시 테스트 대시보드: `sales-progress-dashboard-prototype-20260512-cache.html`
- 기존 프로토타입: `sales-progress-dashboard-prototype-20260512.html`
- 데이터 원본: Google Sheets `raw_orders`, `가공_데이터`, `map_channel`, `map_product`, `map_cost`
- Apps Script 현재 기준: **v3.6** — `apps-script-v3.6.js` (전체 파일. 편집기 코드 위에 그대로 덮어쓰기)

`index.html`은 대시보드 본문을 gzip + base64로 압축해 런타임에 풀어 쓰는 구조입니다.
그래서 `index.html`은 직접 수정하지 않습니다. 수정은 항상 아래 순서로 합니다.

```bash
# 1. dashboard.src.html 수정
# 2. 재생성
python3 build_index.py
# 3. dashboard.src.html을 브라우저로 직접 열어 검증한 뒤 커밋
```

운영 배포 파일은 보호 대상입니다. 검증은 `dashboard.src.html`을 로컬에서 열어 먼저 합니다.

## 40만 행 증가 시 예상

기존 3.3 방식처럼 40만 행 전체를 JSON으로 내려주면 1분 이상 걸리거나 timeout 가능성이 큽니다.

현재 v3.4 캐시 방식은 원본 전체 행이 아니라 `dashboard_cache` 크기에 비례합니다. 현재 패턴이 유지된다면 40만 행에서도 기존 방식보다는 훨씬 안전하지만, `qualityRows`가 같이 커지면 로딩은 다시 늘 수 있습니다.

대략 예상:

- 현재 패턴 유지: `10~25초`
- 품질 이슈 행 증가: `30초 이상`
- 기존 raw 전체 전송 방식: `1~2분 이상` 또는 timeout 위험

- `dashboard_cache`는 삭제하거나 직접 수정하지 않습니다.

## 2026-09-03 데이터 품질 신호 점검

### 왜 품질 신호가 나쁘게 떴는가

품질 패널이 잡아낸 6개 신호는 **서로 독립된 6개 문제가 아닙니다.** 한 행이 여러 신호에
동시에 걸리기 때문에 합계가 실제 문제 행보다 크게 보입니다. 원인은 크게 3덩어리입니다.

1. **매핑 테이블 공백** — `map_product`, `map_cost`에 없는 키가 그대로 통과합니다.
   `가공_데이터`는 매핑 실패를 막지 않고 `미매핑` / 원가 0으로 채워 넣습니다.
2. **숫자가 텍스트로 들어오는 행** — `가공_데이터` 셀이 `33,000` 같은 텍스트일 때
   기존 Apps Script의 `Number(row[3])`은 `NaN`이라 그대로 `0`이 됐습니다.
   이 행은 `매출 0원 품목`과 `마진 음수`에 동시에 잡힙니다.
3. **공백 문자열 통과** — `String(row[8] || '미매핑').trim()`은 셀이 `' '`(공백)일 때
   `''`를 돌려줍니다. 미매핑으로 분류되지도, 정상으로 분류되지도 않고 빈 값이 흘러갔습니다.

### 이번에 고친 것

Apps Script (`apps-script-v3.6.js`)

- `num_()` 추가: 콤마·통화기호·공백이 붙은 텍스트 숫자를 정상 파싱합니다.
  `"33,000"` → `33000`. 기존에는 `0`이었습니다.
- `text_()` 추가: 공백만 있는 셀도 `미매핑` / `미지정`으로 확실히 분류합니다.
- `refreshDashboardCache()`가 품질 항목별 건수(`issueCounts`, `issueText`)를 함께 돌려줍니다.
  `refreshProcessedData()` 실행 직후 alert에서 바로 확인할 수 있습니다.
- `compactQualityRow_()`가 이미 계산한 이슈 배열을 재사용합니다(중복 계산 제거).

대시보드 (`dashboard.src.html`)

- **식별값 강화.** `시트행 추정` 컬럼을 `가공_데이터 행` 칩으로 바꿨습니다.
  칩을 누르면 해당 스프레드시트 행으로 바로 이동합니다.
  이 컬럼은 가로 스크롤 중에도 왼쪽에 고정(sticky)됩니다.
- **주문번호 · 품목명(원본) 컬럼 추가.** 클릭하면 클립보드로 복사됩니다.
  기존 상세 테이블에는 매핑에 실제로 필요한 키인 `품목명(원본)`이 없었습니다.
- **매핑 후보 요약 패널.** 선택한 품질 항목별로 "무엇을 어느 시트에 추가해야 하는지"를
  매출 기준 내림차순으로 보여줍니다. `매핑 후보 CSV` 버튼으로 내려받아 map 시트에 붙여넣으면 됩니다.
  - 채널 미매핑 → `map_channel`에 추가할 `쇼핑몰명`
  - 상품 미매핑 → `map_product`에 추가할 `품목명(원본)`
  - 원가 0/1 → `map_cost`에 추가할 `표준품목명`
- **고유 문제 행(중복 제거) 합계 행 추가.** 6개 신호 단순 합계와 실제 문제 행 수의 차이를 드러냅니다.
- **이슈 배지 컬럼 추가.** 한 행이 몇 개 신호에 걸렸는지 바로 보입니다.
- 상세 표시 한도 120행 → 300행, 정렬을 **매출 내림차순**으로 변경(돈 큰 것부터).
- 표시 행 수 상수는 파일 상단(`SHEET_ID`, `SHEET_TAB`, `QUALITY_DETAIL_LIMIT`, `MAP_CANDIDATE_LIMIT`)에 모았습니다.

버그 수정

- `renderQuality()`가 행 단위 데이터가 없을 때 **집계 행(baseRows)에 품질 조건을 적용**하고 있었습니다.
  집계 행에는 `product`, `cost`가 행 단위 의미로 존재하지 않아 숫자가 무의미했습니다.
  이제 행 단위 데이터가 없으면 안내 문구를 띄웁니다.
- `clean()`(orders 폴백)과 `cleanCacheRow()`(캐시)의 `product` 기본값이 서로 달랐습니다.
  폴백 경로는 표준품목명이 없으면 원본 품목명으로 채워서 **상품 미매핑을 과소 집계**했습니다.
  두 경로 모두 `미매핑`으로 통일했습니다.
- 캐시 응답의 `issueKeys`가 프론트에서 버려지고 있었습니다. 이제 보존합니다.

### 권장 처리 순서

품질 패널은 **현재 선택된 기간 필터 기준**으로 계산됩니다. 전체 기간을 보려면 날짜 범위를 먼저 넓히세요.

1. **채널 미매핑** — 가장 쌉니다. 담당자 미지정과 같은 행이라 `map_channel` 한 번 채우면 두 신호가 같이 사라집니다.
2. **상품 미매핑** — 금액이 가장 큽니다. `매핑 후보 CSV`를 받아 `map_product`에 붙여넣으세요.
3. **원가 0 또는 1** — 조용한 위험입니다. 원가가 비면 마진이 과대계산되어 채널·담당자 실적이 전부 부풀려집니다.
4. **매출 0원 / 마진 음수** — 위 Apps Script 패치를 배포한 뒤 다시 세어야 진짜 숫자가 나옵니다.
   패치 후에도 남는 행은 증정·사은품 등 실제 0원 주문일 가능성이 큽니다.

### 아직 남은 이슈

- `orderCount()`가 캐시 모드에서 `baseRows.orders`를 단순 합산합니다.
  `baseRows`의 `orders`는 (일자 × 채널 × 상품군 × 담당자) 버킷 안의 고유 주문 수라서,
  한 주문이 여러 상품군에 걸치면 **주문 수 KPI가 과대집계**됩니다.
  README 기준 처리 행 52,713 / 고유 주문 44,646이므로 영향 범위가 작지 않습니다.
  주문 수 정의를 확정한 뒤 서버 캐시에 전역 고유 주문 수를 따로 실어 보내는 방식이 맞습니다.
- `readProcessedOrdersForCache_()`가 `가공_데이터` 17개 열을 하드코딩합니다.
  열이 추가되면 조용히 어긋납니다. 헤더명 기반 인덱싱으로 바꾸는 편이 안전합니다.
- `qualityRows` 전량이 첫 응답에 실려 옵니다(약 6,064행). 지연 로딩은 아직 미적용입니다.

## 2026-09-03 Apps Script v3.6 — 갱신 버튼 속도

### 왜 느렸는가

v3.5까지는 `🔄 가공_데이터 갱신`을 누를 때마다 **raw_orders 전체(5만 행+)를 다시 매핑하고,
가공_데이터를 지우고 5만 행 × 17열을 통째로 다시 썼습니다.** Apps Script에서 가장 비싼 작업이
시트 쓰기라서, 행이 늘수록 버튼이 느려지는 구조였습니다.

### v3.6 증분 갱신

| 상황 | 동작 | 비용 |
|---|---|---|
| raw_orders에 행만 늘었을 때 (평소) | 새 행만 매핑해서 가공_데이터 **끝에 추가** | 새 행 수에 비례 |
| 아무 변화 없을 때 | 매핑 시트만 읽고 끝. "변경 없음" 표시 | 수 초 |
| map_channel / map_product / map_cost / 출고배송비를 고쳤을 때 | **자동으로 전체 재생성** | 예전과 같음 |
| raw_orders 행이 줄었거나 순서·첫 행·마지막 행이 바뀌었을 때 | 자동으로 전체 재생성 | 예전과 같음 |
| `🧹 가공_데이터 전체 재생성` 메뉴 | 무조건 전체 재생성 | 예전과 같음 |

판단 근거는 문서 속성(`OURBOX_PROC_STATE`)에 저장된 이전 실행 상태입니다.
매핑 시트 서명(`mapSig`)에서 표준품목명이 빈 map_product 행은 제외하므로, 새 품목이 자동 추가돼도
증분이 유지되고 **사람이 표준품목명을 채우는 순간** 전체 재생성으로 전환됩니다.

증분 갱신이 놓치는 경우 하나: **raw_orders의 기존 행을 제자리에서 고친 경우**(예: 실결제금액 수정).
행 수·순서가 그대로라 감지하지 못합니다. 이때는 `🧹 전체 재생성`을 누르세요.

### 그 밖의 v3.6 변경

- 완료 alert에 단계별 소요 시간(`매핑 로드 / raw 읽기 / 가공_데이터 쓰기 / 캐시 생성 ...`)이 뜹니다. 느리면 어디가 느린지 이 숫자로 판단합니다.
- `num_()` / `text_()`: 텍스트 숫자·공백 셀 처리를 raw 매핑 단계에도 적용했습니다. **'매출 0원 품목' 신호는 이 버전 배포 후 다시 세야 진짜 숫자입니다.**
- `qualityRows`에서 대시보드가 쓰지 않는 `ship / settlement / shipCost`를 뺐습니다(전송량 감소).
- 캐시 meta에 `spreadsheetId`, `processedSheetGid`, `issueCounts`가 실립니다.

### 배포 순서

1. Apps Script 편집기 → 기존 코드 전체 선택 → `apps-script-v3.6.js` 내용으로 교체 → 저장
2. **배포 관리 → 기존 배포 → 새 버전** (URL 유지). 새 배포를 만들면 `dashboard.src.html`의 `API_URL`도 바꿔야 합니다
3. 시트 새로고침 → 메뉴 `📊 아워박스` → `🔄 가공_데이터 갱신 (증분)` 1회 실행. 첫 실행은 상태가 없어서 전체 재생성입니다(예전 속도). 두 번째부터 증분입니다
4. alert의 `품질 신호:` 줄과 `소요 시간:` 줄을 확인
